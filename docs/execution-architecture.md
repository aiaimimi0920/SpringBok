## 1. 本次决定

第一条产品链**保留现有 Workers / SQLite Durable Object / Node 出站桥 / Komodo 适配**，不引入 SSH、通用远程 shell、另一个执行引擎或自建云端常驻服务。固定测试链与真实服务链分开；现有单次 fixture 不通过删除限制“升级”为通用执行器。

这是为了复用已核对的完整配置、精确 Update ID、镜像/容器证据和中断阻断，而不是认为 Komodo 已满足全部产品要求。后续节点安装必须显示完整依赖与资源成本；未经容量和许可确认，不安装或分发集成包。

首版拓扑选择**每个已授权执行隔离单元管理一台目标服务器**：Core、Mongo、Periphery 位于该服务器的专用 rootless Docker 环境内；一个 SpringBok 控制面管理多个独立隔离单元。暂不搭建共享中央 Core，也不由 Cloudflare 直连 Core。这样避免首次多节点改造同时引入跨服务器 Core 通信、共享数据库和跨主机故障域。

代价是每台执行服务器暂时都有 Core/Mongo 开销。小内存服务器不满足预检查时，只能监控或暂不接入执行，不能自动降低隔离、借用其他业务数据库或隐藏安装这些依赖。是否改为共享 Core/轻量原生 Docker 适配器，必须由真实资源测量或许可要求触发独立设计，不扩展本任务。

## 2. 控制面、执行和监控的责任分离

```text
浏览器 ──Access 身份/同源 API──> Worker + Static Assets
                                  │
                     目录/权限 ──> 节点独立任务 DO    监控存储（ARC-02）
                                  ↑                         ↑
                    出站领取/回报 │                         │ 独立指标/心跳入口
                                  │                         │
目标服务器：                执行桥容器                  主机只读采集进程
                            │               无 Core/部署凭据
                 内部 Core → Periphery      无 Docker socket
                    │            │
                 本地 Mongo   专用 rootless daemon → 业务容器
```

| 责任方 | 唯一职责 | 明确不做 |
| --- | --- | --- |
| Worker/API | 验证主体、资源归属、操作权限、schema 和限制；提供 UI；协调请求 | 不运行 Docker、不保存节点文件日志、不接收用户任意命令/URL |
| 节点任务 DO | 当前任务权威状态、不可变计划绑定、一次领取、回执、操作者关联 | 不把 D1/KV 查询副本当授权真相；不保存高频监控时序 |
| 目录存储 | 服务器/服务 ID、所有者、状态和允许能力 | 不凭客户端提供的 ID 宣布其已获授权；具体 schema 归 ARC-02/C04 |
| 执行桥 | 拉取本节点任务；先落本地意图，再调用固定适配器；保存并回传结果 | 不执行远程传来的脚本；无宿主 Docker socket 挂载；不自行批准生产 |
| Komodo 适配器 | 固定 API、完整配置校验、写入、Deploy、精确 Update/容器证据 | 不透传任意 Core API、Action、Procedure、终端或参数 |
| Core/Mongo/Periphery | 保留原有执行依赖；Mongo 存 Core 自身数据，Periphery 控制隔离 daemon | 不承担 SpringBok 云端任务主记录；管理端口不对公网开放 |
| 主机只读采集进程 | 用普通用户权限采集主机指标/时间戳，以仅监控凭据出站上报 | 不持有 Core 密码、执行凭据或 sudo 权限，不读业务文件/环境变量 |

监控进程在**宿主 Linux**运行，避免把执行桥容器自己的 CPU、内存、磁盘数据冒充整台服务器。它与执行桥可共用安装包/配置格式，但进程、凭据和最小权限分离。不能以挂宿主 `/proc`、`/sys`、根目录或 Docker socket 到通用容器作为未经审查的捷径。

现有 Compose 只有执行桥，没有主机采集进程；本页不是已完成安装器。N06/N07 应同时说明这两个角色及其启动/停止/升级生命周期。

## 3. 节点身份、注册与撤销

身份模型是 `ownerId → nodeId → capability`。`nodeId` 由可信服务端登记，不能将请求体中的名字当认证。首版仍是私有单管理员产品，不提前引入租户计费或多组织管理。

1. N02 的加入请求必须由已验证管理员发起，使用有期限、一次性的加入凭据；重复兑换或绑定不同节点拒绝。
2. N03 为执行桥与采集角色提供独立凭据，至少区分 `execute` 和 `observe`。采集凭据不能领取/回报部署任务，执行凭据不能代替用户批准。
3. Worker 验证凭据绑定的节点/角色后才能路由对应 DO；不能先按调用者的 `nodeId` 查数据，再信任回执中的节点名。
4. 轮换/撤销的精确状态与权威存储由 ARC-02/N04/N05 定义；旧凭据不得因 KV 缓存陈旧而继续获得新任务。历史审计和未知任务不随撤销删除。
5. 节点被视为该服务器执行证据的受托来源，不宣传其回报能抵抗节点本身恶意伪造。关键上线仍有独立业务验收。

当前单个 `NODE_TOKEN` 与 `pc2-test` 仅保留在旧测试协议中，不复制成生产共享密码，也不让“新增服务器”页面修改这些常量。

## 4. 任务与恢复不变量

| 阶段 | 必须持久化/验证 | 中断时的处理 |
| --- | --- | --- |
| 生成计划 | 可信目录、主体、节点/服务/环境、不可变制品、完整配置摘要、协议/计划版本 | 任一输入变化，旧确认失效；预览不写任务、不产生批准 |
| 提交 | 同一节点权威事务内绑定 request ID、完整输入、actor 与 revision | 同 ID 同输入返回原记录；同 ID 不同输入拒绝 |
| 领取 | DO 先提交 claimed，再返回一次任务 | 领取响应丢失不重投；超时转 unknown，不能租约到期就自动再执行 |
| 节点开始 | 本地独占日志记录 intent；执行前核对资源身份和完整配置 | 只有 intent 而无明确结果时保留 unknown，不以重启消除记录 |
| 执行与核对 | 只调用该计划允许的适配器；绑定精确 Update ID、目标、镜像/容器、配置和健康证据 | 只允许只读核对已知执行 ID；不知道是否发出的写操作不能盲重试 |
| 回报 | 节点先持久保存结果，再上报；DO 校验归属、顺序和绑定 | 可重送同一份结果，不重做部署；晚到结果不能解除已未知的任务 |

每节点首版最多一个未完成的有副作用任务。**心跳、只读指标和日志查询不进入该执行队列**；执行节点离线时监控仍可展示最后观测及陈旧标志，指标存储故障也不能伪造部署失败/成功或触发重放。

业务成功需要真实应用就绪，不能仅凭 Core 接收请求或容器启动。数据库迁移有独立组件回执与恢复策略；镜像回滚不等于数据回滚。D13/D16 未完成的产品不能靠四样例契约跳过这些门槛。

## 5. 现有协议如何扩展而不破坏历史证据

现有 `cloud/protocol.mjs` 的固定 `NODE`、两种 operation、100 条上限、fixture 一次消费和 `deploymentVerified=false` 继续保留。E01–E10 的历史 evidence、测试身份和样例 ID 不改写。

N01 引入**明确版本化的新节点协议及独立存储空间**，不是放宽旧 `submission()`：

- 新入口使用经认证的节点上下文，并校验存储记录版本；旧数据仍由旧解析器读取。
- 新任务绑定 `ownerId/nodeId/serviceId/environment/requestId/planDigest/protocolVersion`；字段由服务端/可信 resolver 生成，不能把 UI 自报 actor 或目标当授权。
- 固定 fixture 不能通过新通用节点入口自动执行；新协议未知版本/未知操作一律拒绝。
- 新协议从只读连通与节点隔离证明开始，真实部署操作在 D07/D09/D10 中单独接入。不要先提供一个通用 dispatch 后再补授权。
- 新旧版本并存期间，已领取的旧任务留在旧日志/DO 中核对；不搬运为新 queued 任务。回退版本前必须确认新任务可被安全保留/只读处理，不能删除新 DO 假装回滚成功。

具体路由、凭据索引、目录 schema 和跨对象一致性由 ARC-02 明确后再编码；本任务不预先声明这些接口已经可调用。

## 6. 权限、网络与资源门槛

沿用当前模板的内部 Core/Mongo/Periphery 网络；执行桥只向固定 HTTPS Worker origin 出站。不为管理通道增加公网 Core/Mongo 端口、Tunnel、SSH 或宿主 daemon 权限。业务服务公网入口与控制通道分别授权。

Periphery 虽关闭终端，仍能控制**该 rootless daemon 下的全部资源**；容器名字或 label 不是隔离边界。专用账户/daemon、socket 所有权、cgroup 限额、网络及已有业务不受影响，都必须在安装预检查与实际验收中确认。

当前测试模板硬上限为 Mongo 1 GiB、Core 1 GiB、Periphery 512 MiB、bridge 128 MiB；单 fixture 另限 128 MiB，合计约 2.75 GiB。CPU 限额总和约 3.5 核。这是**限额之和，不是实测占用、最低配置或容量保证**；真实业务、主机采集器、磁盘增长、系统余量尚未计入。不得将这个数字直接写成用户服务器规格推荐。

常驻节点默认设计目标为至少 30 秒轮询、失败指数退避并带抖动/最大间隔；网络恢复只恢复读取/回报，不自动重做 unknown 写操作。一个角色一个受管理实例，存在日志锁时先核对原进程，不盲删锁。频率/上限的最终值在 N07 实测后固定；当前 CLI 仍只执行一次。

观测角色必须独立限制采样、上报批量、重试与离线缓存。监控存储不可用时丢弃/降采样的规则属于 ARC-02/M06，不能无限写本地磁盘或拿部署日志作指标缓冲。

- [Workers 文件系统](https://developers.cloudflare.com/workers/runtime-apis/nodejs/fs/) 明确 `/tmp` 不持久化、属于单次请求；因此 Linux journal 不能移到 Worker 临时目录作为权威状态。
- [SQLite DO 事务](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#transactionsync) 明确 `transactionSync` 仅用于 SQLite-backed DO、同步完成、抛异常回滚；跨 DO、网络调用和 D1 写入不能宣称在同一事务中。

未查询或修改真实 Cloudflare 账户计划；不承诺零费用。镜像 digest、目标架构、具体账户配额、域名及实际部署授权仍属于 V01/V02/N06 的门槛。

## 8. 取舍、未决项和下一任务

| 方案 | 本轮决定 | 原因 / 重新考虑的条件 |
| --- | --- | --- |
| 保留现有 Komodo 适配 | 作为首条产品链的实现基线 | 复用已验证执行证据；实际容量/许可不合适时另开替代任务 |
| 共享中央 Core/Mongo | 暂不采用 | 首次多节点先隔离故障与权限，避免同时引入跨主机执行网络 |
| 自写 Docker 执行器 | 暂不采用 | 当前无实现/恢复证据，不能为“轻量”一次重写并扩大权限 |

| 把 Core/Mongo 搬到 Workers/Containers | 不采用 | 不把控制面平台等同于已有执行服务的兼容持久运行环境 |
| 整机指标从宿主只读采集 | 采用职责划分，代码待 N07/M01–M06 | 不误报容器自身资源；新增角色必须落实权限和生命周期 |
